# PART 2 개념정리 — 연결: RAG

이 문서는 강의 「AI 리터러시 · 프롬프트 엔지니어링 · RAG」의 **PART 2(s08–s12 중심, s13 정리 포함)** 를 뒷받침하는 개념 참고서다. PART 2의 주제는 강의 부제의 뒤 축 — **"신뢰할 수 있는 정보를 연결한다"** — 이고, 앞 축인 **"모델을 이해해 올바르게 지시한다"** 는 짝이 되는 문서 `part1-리터러시와-프롬프트.md`에 있다. 토큰과 컨텍스트 윈도우, 다음 토큰 예측과 온도, 프롬프트의 여섯 요소와 세 패턴, 구조화 출력은 그쪽에서 이미 다뤘으므로 여기서는 필요한 곳에서 절 번호로 되짚기만 한다.

이 문서가 다루는 것은 **RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 하나다. 모델이 답하기 전에 질문과 관련된 문서를 찾아, 그 문서를 근거로 프롬프트에 함께 넣어준 뒤 답을 만들게 하는 방법이다. PART 1 6절이 정리한 세 한계 중 **환각과 지식 컷오프**를 정면으로 겨냥한 처방이며, 「모델을 더 똑똑하게 만든다」가 아니라 **「모델이 볼 자료를 우리가 고른다」** 는 발상이다.

읽는 방식은 PART 1과 같다. 각 절은 **정의 → 원리(왜 그런가) → 구체 사례 → 인용 → 대응 슬라이드** 순서이고, 영어 원어는 처음 등장할 때 `한글(English)` 형태로 병기한 뒤 그다음부터는 한글만 쓴다. 도식은 코드 블록 안의 텍스트 그림, 표는 강의 데모 화면과 짝을 이루도록 만들었다. 데모에 나오는 유사도 0.94/0.71/0.28/0.05, policy-04 같은 문서 id, 실패 유형 네 가지는 슬라이드와 **같은 값**을 그대로 쓴다.

전체 얼개는 이렇다. 1절은 **왜 RAG인가**(파인튜닝과의 갈림길), 2절은 **무엇이 검색을 가능하게 하는가**(벡터와 코사인 유사도), 3~6절은 **파이프라인을 앞에서부터**(색인 → 청킹 → 검색 → 리랭킹), 7~8절은 **찾은 것을 어떻게 쓰는가**(증강과 출처 표기), 9~10절은 **무엇이 깨지고 그것을 어떻게 재는가**(실패 카탈로그와 평가)다. 11절은 인용 문헌과 슬라이드 대응표다.

## 1. RAG가 푸는 문제 — 왜 검색이 컷오프와 환각을 메우는가

**정의.** RAG는 생성 직전에 외부 지식 저장소에서 질문과 관련된 문서를 **검색(retrieval)** 해, 그것을 프롬프트에 근거로 **증강(augmentation)** 한 뒤 답을 **생성(generation)** 하는 구조다. 모델 가중치는 건드리지 않는다. 바뀌는 것은 오직 **모델이 그 순간 보는 문맥**이다.

**원리(왜 검색이 이 문제를 메우는가).** LLM이 가진 지식은 학습 과정에서 가중치에 압축된 **파라메트릭 지식(parametric knowledge)** 이다. 압축이므로 원문이 그대로 들어 있지 않고, 갱신하려면 다시 학습해야 하며, 어떤 문서 때문에 그 답이 나왔는지 되짚을 수 없다. RAG가 붙이는 것은 그 반대 성질의 **비파라메트릭 지식(non-parametric knowledge)** 이다 — 저장소에 원문 그대로 있고, 파일 하나만 갈아 끼우면 즉시 갱신되며, 어느 문서를 썼는지 id로 남는다.

여기서 「왜 검색이 환각을 줄이는가」가 논리적으로 따라 나온다. PART 1 3·6절에서 본 대로 모델은 다음 토큰의 확률분포에서 하나를 고른다. 근거가 없는 상태에서 「환불 기한은 며칠인가」를 물으면, 그 자리를 채울 가장 그럴듯한 토큰은 학습 말뭉치의 통념(「보통 30일」)이다. 그런데 창 안에 「환불은 구매일로부터 14일 이내」라는 문장이 들어 있으면, **조건부 확률의 조건 자체가 바뀌어** 그 문장을 이어 쓰는 쪽이 압도적으로 그럴듯해진다. RAG는 모델에게 사실 검증 능력을 부여하는 것이 아니라, **정답이 문맥 안에 있게 만들어 확률의 지형을 바꾸는** 장치다.

이 설명은 동시에 RAG의 한계도 알려준다. 근거를 창에 넣는 것과 모델이 그것을 **쓰는** 것은 다른 일이다. 지시가 약하면 모델은 여전히 자기 기억을 꺼내 쓴다(9절의 「근거 무시」). 그래서 8절의 근거 사용 강제와 출처 표기가 RAG의 선택 사항이 아니라 필수 부품이 된다.

모델이 모르는 지식을 붙이는 길은 크게 둘이고, 갈림길에서 무엇을 고를지는 **지식이 얼마나 자주 바뀌는가**와 **출처를 대야 하는가**로 거의 결정된다.

| 비교 축 | RAG | 파인튜닝(fine-tuning) |
|---|---|---|
| 지식이 놓이는 곳 | 외부 저장소의 원문. 답할 때마다 창으로 불러온다 | 모델 가중치 안. 답할 때 이미 들어 있다 |
| 비용 | 초기 색인 비용 + **매 호출마다** 근거 문서 토큰값. 호출당 비용이 늘어난다 | 학습 1회에 큰 비용(데이터 구축·GPU). 이후 호출당 추가 토큰은 없다 |
| 지식 신선도 | 저장소를 갱신하면 **다음 질문부터 즉시** 반영된다 | 데이터를 모아 다시 학습해야 반영된다. 그 사이 답은 낡은 채로 나간다 |
| 추적성(traceability, 출처) | 어느 문서를 근거로 썼는지 id로 답변에 붙일 수 있다. 사람이 원문을 열어 검증 가능 | 왜 그 답이 나왔는지 특정 문서로 되짚기 어렵다 |
| 구축 난이도 | 파이프라인이 길다(로드·청킹·임베딩·검색·리랭킹·증강). 손댈 조절 항목이 많다 | 파이프라인은 짧지만 **데이터 품질이 전부**다. 잘못 학습되면 되돌리기 어렵다 |
| 잘 맞는 상황 | 자주 바뀌는 사내 규정·최신 뉴스·제품 문서. 「정확해야 하고 출처를 대야 하는」 사실 | 고정된 말투·서식·도메인 어휘, 특정 출력 스타일, 분류 같은 반복 과제 |
| 잘 못하는 것 | 문서에 없는 것은 여전히 못 한다. 검색이 틀리면 그대로 틀린다 | 사실 갱신. 「알고 있게」 만들 수는 있어도 「어제 바뀐 것」을 담지 못한다 |

한 줄로 줄이면 이렇다 — **파인튜닝은 「어떻게 말할지」를 가르치고, RAG는 「무엇을 말할지」를 그 자리에서 건넨다.** 둘은 배타적이지 않아 실무에서는 자주 함께 쓰이지만, 최신·사내 사실 문제에 부딪혔을 때 먼저 꺼낼 카드는 거의 언제나 RAG다.

**구체 사례.** 강의 데모(s10)는 같은 질문 「우리 회사 환불 정책은 며칠까지 가능해?」를 RAG를 켠 채와 끈 채로 나란히 굴린다. 끈 쪽은 검색·증강 단계가 통째로 비어 있고, 생성 단계에서 **「보통 30일 정도면 되는 경우가 많습니다 (근거 없음 — 실제와 다를 수 있음)」** 를 내놓는다. 켠 쪽은 policy-04(0.94)·policy-07(0.71)을 찾아 근거로 주입한 뒤 **「환불은 구매일로부터 14일 이내, 미개봉 상품 한정 (근거: policy-04)」** 로 답한다. 두 답의 차이는 모델의 능력 차이가 아니다. 같은 모델이 **다른 문맥**을 본 결과다.

**인용.** Lewis, P. et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*, NeurIPS 2020(arXiv:2005.11401) — 검색기(retriever)와 생성기(generator)를 결합해, 파라메트릭 지식만으로는 풀기 어려운 지식 집약적 과제의 정확도를 끌어올리는 구조를 제안한 논문. 오늘날 실무에서 말하는 RAG의 원형이다.

## 2. 벡터와 의미 — 임베딩과 코사인 유사도

**정의.** **임베딩(embedding)** 은 텍스트를 의미가 담긴 고정 길이의 숫자 벡터로 바꾸는 것이다. 뜻이 비슷한 문장은 서로 가까운 곳에, 뜻이 다른 문장은 먼 곳에 놓이도록 학습된 좌표계다. **코사인 유사도(cosine similarity)** 는 두 벡터가 이루는 각도의 코사인 값으로 그 「가까움」을 재는 척도이며, 값은 −1(정반대) ~ 0(무관) ~ 1(같은 방향) 사이에 놓인다.

**원리(왜 문자열이 아니라 벡터인가, 왜 각도로 재는가).** 문자열을 그대로 비교하면 「환불」과 「반품」, 「며칠까지」와 「기한」처럼 **표현은 다르지만 뜻이 같은** 쌍을 잡아낼 수 없다. 반대로 「환불 규정」과 「환불 불가 품목」처럼 글자가 겹치는데 뜻이 다른 쌍은 잘못 잡는다. 임베딩 모델은 **분포 가설(distributional hypothesis)** — 비슷한 문맥에 등장하는 표현은 비슷한 뜻을 가진다 — 위에서 학습되므로, 글자가 하나도 겹치지 않아도 같은 맥락에서 쓰이는 문장을 가까이 놓는다.

각도를 쓰는 이유는 **의미를 담는 것이 벡터의 방향이기 때문**이다. 코사인은 분모에서 두 벡터의 길이로 나눠 **길이 성분을 소거하고 방향만 남긴다** — 벡터의 크기가 얼마든 「어느 쪽을 가리키는가」만으로 가까움을 판정한다는 뜻이고, 덕분에 값이 언제나 −1~1의 고정 범위에 놓여 임계값을 문서를 가로질러 비교할 수 있다. 다만 임계값의 적정 수준은 모델마다 다르므로, 모델을 바꾸면 다시 잡아야 한다.

여기서 한 가지는 분명히 해 둘 필요가 있다. 실무에서 쓰는 임베딩 모델은 대부분 **길이가 1로 정규화(L2 normalization)된 벡터**를 내놓는다. 이 경우 분모가 1이 되어 코사인은 내적과 같아지고, 유클리드 거리도 코사인의 단조 감소 함수(‖q−d‖² = 2 − 2·cos)가 되어 **두 척도가 같은 순위를 낸다.** 즉 정규화된 벡터에서는 「각도냐 거리냐」가 실제 검색 결과를 가르지 않는다. 각도로 이야기하는 이유는 순위가 달라져서가 아니라, 값의 범위가 고정되어 해석하기 쉽고 정규화되지 않은 벡터에도 그대로 통하기 때문이다. 식은 이렇다.

```
                 q · d              q₁d₁ + q₂d₂ + … + qₙdₙ
  cos(q, d) = ───────────  =  ────────────────────────────────────
                |q| |d|        √(q₁²+…+qₙ²) · √(d₁²+…+dₙ²)

  분자 = 내적 — 두 벡터가 같은 방향으로 얼마나 겹치는가
  분모 = 두 벡터의 길이 — 나눠 줌으로써 '길이' 성분을 소거한다
```

**구체 사례 — 손으로 따라가는 코사인 계산.** 실제 임베딩은 수백~수천 차원이지만, 원리는 3차원에서 그대로 성립한다. 아래 벡터는 s09 표의 네 행 중 **1순위(0.94)** 와 **탈락(0.28)** 에 대응하도록 고른 설명용 3차원 값이다(표의 벡터 표기와 마찬가지로 실제 모델의 출력이 아니다). 길이를 1로 맞추지 않은 값을 일부러 골랐다 — 그래야 ②의 길이 계산과 ③의 나눗셈이 눈에 보인다. 정규화된 실제 모델의 벡터라면 ②의 두 길이가 모두 1이라 ①의 내적이 그대로 코사인 값이 된다. 슬라이드 표에 적힌 벡터(`[0.82, -0.11, 0.44, …]` · `[0.12, 0.55, -0.20, …]`)는 여기와는 별개로 스케치한 예시값이라, 아래 3차원 벡터가 그 표 벡터의 앞 세 성분은 아니다 — 두 예시는 서로 다른 숫자로 같은 이야기를 보여줄 뿐이다.

```
  질문 q  "환불은 며칠까지 되나요?"                  = ( 0.80, -0.40,  0.40)
  문서 A  "환불은 구매일로부터 14일 이내 가능합니다" = ( 0.88, -0.08,  0.42)
  문서 B  "배송은 영업일 기준 2~3일 걸립니다"        = ( 0.31,  0.50,  0.36)
```

**첫째 쌍 (q, A) — 뜻이 가까운 쌍.**

```
  ① 내적    q · A = 0.80×0.88 + (-0.40)×(-0.08) + 0.40×0.42
                  = 0.704      + 0.032          + 0.168      = 0.904

  ② 길이    |q| = √( 0.80² + (-0.40)² + 0.40² ) = √(0.64 + 0.16 + 0.16)       = √0.96   = 0.980
            |A| = √( 0.88² + (-0.08)² + 0.42² ) = √(0.7744 + 0.0064 + 0.1764) = √0.9572 = 0.978
                             └ 제곱하면 부호가 사라진다. 길이는 방향과 무관한 크기다.

  ③ 나눗셈  cos(q, A) = 0.904 / (0.980 × 0.978) = 0.904 / 0.9584 = 0.943
```

**둘째 쌍 (q, B) — 뜻이 먼 쌍.**

```
  ① 내적    q · B = 0.80×0.31 + (-0.40)×0.50 + 0.40×0.36
                  = 0.248      - 0.200        + 0.144        = 0.192
                               └ 부호가 반대인 성분이 내적을 깎는다

  ② 길이    |B| = √(0.31² + 0.50² + 0.36²) = √(0.0961 + 0.25 + 0.1296) = √0.4757 = 0.690
            |q| 는 위와 같다 = 0.980

  ③ 나눗셈  cos(q, B) = 0.192 / (0.980 × 0.690) = 0.192 / 0.6762 = 0.284
```

**0.943과 0.284** — s09 표의 1순위 **0.94**, 탈락 **0.28** 과 같은 자리에 떨어진다. 두 계산의 차이는 ①에서 이미 갈렸다. A는 세 성분이 모두 q와 같은 부호라 셋 다 내적에 보탬이 되지만, B는 둘째 성분의 부호가 반대라 −0.200을 깎아 먹는다. **부호가 엇갈리는 축이 있다는 것은 「그 의미 축에서 반대쪽에 있다」는 뜻**이고, 그것이 곧 각도가 벌어지는 이유다.

같은 일을 2차원으로 줄여 그림으로 보면 이렇다. 유사도 값은 각도의 코사인이므로, 표의 네 수치는 그대로 네 개의 사이각으로 읽힌다.

```
      의미 축 2   ▲
   (사람·조직)    │
                  │
  ● 채용 공고는   │
    상시 게시     │      ● 배송은 영업일 기준 2~3일
                  │
                  │            ★ 질문 "환불은 며칠까지 되나요?"
                  │           ● 환불은 구매일로부터 14일 이내   ← 사이각 약 20° · cos 0.94
                  │             ● 교환은 수령 후 7일 이내       ← 사이각 약 45° · cos 0.71
                  │
──────────────────┼──────────────────────────────────────────────► 의미 축 1
                원점                                            (구매 후 처리)

  재는 것은 점의 위치가 아니라, 원점에서 뻗어 나간 두 화살표의 '사이각'이다.
  ★–배송 문장은 약 74°(cos 0.28), ★–채용 문장은 약 87°(cos 0.05)까지 벌어진다.
  화살표를 모두 길이 1로 맞춰 그리면(정규화) 끝점이 하나의 원 위에 놓이고, 사이각 순서와
  끝점 사이 거리 순서가 일치한다 — 실제 임베딩 모델의 출력이 대개 이 상태다.
  실제 축은 사람이 이름 붙일 수 있는 개념이 아니라 학습으로 정해진 수백 개의 차원이다.
```

s09 데모 표는 이 네 문장을 그대로 놓고, 질문과의 유사도가 높은 순으로 **top-k개만 통과시킨다.** 0.94와 0.71은 통과, 0.28과 0.05는 탈락이다. 여기서 이미 다음 절들의 질문이 떠오른다 — 임계값을 어디에 둘 것인가, k를 몇으로 할 것인가, 그리고 애초에 「문장 하나」가 검색 단위로 적절한가(4절).

**인용.**
- Mikolov, T., Chen, K., Corrado, G., Dean, J., *Efficient Estimation of Word Representations in Vector Space*, 2013(arXiv:1301.3781) — 단어를 밀집 벡터로 표현하면 의미 관계가 벡터 연산으로 드러남을 대규모로 보인 연구(word2vec). 「의미를 좌표로 옮긴다」는 발상의 출발점이다.
- Reimers, N., Gurevych, I., *Sentence-BERT: Sentence Embeddings using Siamese BERT-Networks*, EMNLP 2019(arXiv:1908.10084) — 문장 단위 임베딩을 코사인 유사도로 바로 비교할 수 있도록 학습하는 방법을 제시했다. 오늘날 RAG의 문서 임베딩이 이 계열이다.

**대응 슬라이드: s09**

## 3. 인덱싱 파이프라인 — 미리 만들어 두는 쪽과 질문마다 도는 쪽

**정의.** **색인(indexing)** 은 원본 문서를 검색 가능한 형태로 미리 가공해 두는 과정이며 네 단계로 이뤄진다 — **로드 → 청킹(chunking) → 임베딩 → 저장.** 이 네 단계는 사용자의 질문과 무관하게 **오프라인**에서 돌고, 질문이 들어오는 **런타임**에는 이미 만들어진 결과를 읽기만 한다.

**원리(왜 시점을 나누는가).** 질문 한 건이 들어올 때마다 사내 문서 10만 건을 읽어 임베딩한다면, 응답에 몇 분이 걸리고 비용은 감당할 수 없다. 그래서 **비싸지만 한 번만 해도 되는 일**(문서를 벡터로 바꾸는 일)을 앞으로 빼두고, **싸지만 매번 해야 하는 일**(질문 하나를 벡터로 바꾸고 가까운 것을 찾는 일)만 런타임에 남긴다. 이 분리가 RAG를 실용적으로 만드는 핵심 설계다.

시점을 나누면 반드시 따라오는 규칙이 하나 생긴다. **색인된 벡터와 질의 벡터는 같은 임베딩 공간에 놓여야 한다.** 공간이 다르면 좌표계 자체가 달라서, 두 벡터의 코사인 값은 의미와 아무 상관 없는 숫자가 된다. 실무에서 이 조건은 대개 「양쪽에 같은 모델을 쓴다」로 지켜지지만, 규칙의 본체는 모델이 아니라 **공간**이다 — DPR(Dense Passage Retrieval, 5절 인용)처럼 질문 인코더와 문서 인코더를 따로 두는 구조가 성립하는 것도, 두 인코더를 **함께 학습시켜 하나의 좌표계를 공유하게** 만들었기 때문이다. 금지되는 것은 서로 무관하게 학습된 두 모델을 양쪽에 갖다 붙이는 일이다. 그리고 이 규칙은 실무에서 「임베딩 모델(또는 함께 학습된 인코더 쌍)을 바꾸려면 전체 문서를 다시 색인해야 한다」는 비용으로 나타난다 — 모델 교체는 설정 한 줄이 아니라 재구축 작업이다.

```
┌─ 색인 시점 (오프라인) — 문서가 추가·수정될 때만 실행한다 ────────────────────┐
│                                                                              │
│ 원본 문서 ──(1) 로드──► 평문 ──(2) 청킹──► 청크 N개 ──(3) 임베딩──► 벡터 N개 │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────┬───┘
                                                                           │  (4) 저장 — 벡터와 원문 청크를 함께 넣는다
                                                           ┌───────────────┴───┐
                                                           │ 벡터 저장소       │
                                                           │ (인덱스)          │
                                                           └───────────────┬───┘
                                                                           │  (6) 검색 — 질의 벡터와 가까운 top-k 청크를 읽는다
┌─ 질의 시점 (런타임) — 요청 한 건마다 실행한다 ───────────────────────────┴───┐
│                                                                              │
│ 질문 ──(5) 질의 임베딩──► 질의 벡터 ──► 상위 청크 k개                        │
│                                                                              │
│      ──(7) 증강──► 근거가 박힌 프롬프트 ──(8) 생성──► 출처가 달린 답변       │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

s10 데모가 보여주는 다섯 단계 — 질문 → 임베딩 → 검색 → 증강 → 생성 — 은 이 그림의 **아래쪽 레인, 즉 질문 입력과 그에 이어지는 (5)~(8)** 이다(첫 단계인 「질문」은 번호 붙은 연산이 아니라 레인의 입력이다). 위쪽 레인은 데모에 나오지 않지만, 위쪽이 잘못되어 있으면 아래쪽은 무엇을 해도 고쳐지지 않는다. 9절의 실패 유형 절반이 위쪽에서 발생한다.

**구체 사례.** 네 단계의 입력·출력·흔한 실패는 이렇다. 「흔한 실패」 열은 그대로 9절 카탈로그의 원인 항목으로 이어진다.

| 단계 | 입력 | 출력 | 흔한 실패 | 알아채는 법 |
|---|---|---|---|---|
| (1) 로드 | PDF·HTML·워드·표·사내 위키 | 평문 텍스트 + 메타데이터(제목, 문서 id, 유효일자, 접근 권한) | 스캔 PDF·이미지·복잡한 표를 읽지 못해 본문이 **빈 문자열**로 들어온다. 머리말/바닥글·목차가 본문에 섞인다 | 문서 수 대비 추출 글자 수를 대조한다. 글자 수 0에 가까운 문서 목록을 뽑아 본다 |
| (2) 청킹 | 평문 텍스트 | 청크 N개(각각 원문 문자열 + 출처 메타데이터) | 문장·표·코드 블록 한가운데를 잘라 의미가 끊긴다. 청크가 너무 커서 한 덩어리에 여러 주제가 섞인다 | 청크 길이 분포를 본다. 극단적으로 짧거나 긴 꼬리를 표본으로 열어 읽는다 |
| (3) 임베딩 | 청크 N개 | 벡터 N개(모두 같은 차원) | 도메인·언어에 맞지 않는 모델을 써서 유사도가 뭉개진다. 청크가 모델의 최대 입력 길이를 넘어 **뒷부분이 조용히 잘린다** | 대표 질문 20개로 정답 청크가 상위에 오는지 눈으로 확인한다(10절의 recall@k) |
| (4) 저장 | 벡터 N개 + 원문 청크 + 메타데이터 | 검색 가능한 인덱스 | 벡터만 저장하고 원문을 안 넣어 나중에 프롬프트에 붙일 텍스트가 없다. 문서가 갱신됐는데 옛 벡터가 남아 **중복**된다 | 문서 id별 청크 수를 세어 갱신 전후를 비교한다 |

메타데이터는 「나중에 필요하면 붙이자」로 미루기 쉬운데, 실제로는 (1)에서 놓치면 뒤에서 복구할 수 없다. 유효일자가 없으면 9절의 최신성 실패와 상충 근거를 처방할 수 없고, 접근 권한이 없으면 권한 누수를 막을 수 없다. **로드 단계에서 챙길 것은 본문뿐이 아니라 「이 텍스트가 어디서 왔는가」 전부**다.

**인용.**
- Lewis et al.(2020, 1절 인용) — 문서 인덱스를 미리 구축해 두고 질의 시점에는 검색만 수행하는 구조가 여기서 제시되었다.
- Johnson, J., Douze, M., Jégou, H., *Billion-scale similarity search with GPUs*, 2017(arXiv:1702.08734) — 대규모 벡터 인덱스를 실제로 구축·질의하는 기법을 정리한 연구(FAISS). 게재처는 확인하지 않았으므로 저자·제목·연도만 밝힌다.

**대응 슬라이드: s10**

## 4. 청킹 전략 — 무엇을 검색의 한 조각으로 삼을 것인가

**정의.** 청킹은 문서를 검색의 단위인 **청크**로 쪼개는 작업이다. 청크는 두 가지 역할을 겸한다 — **임베딩되어 검색 대상이 되는 단위**이자, 검색된 뒤 **프롬프트에 통째로 실려 들어가는 단위**다.

**원리(왜 크기가 트레이드오프인가).** 이 이중 역할이 정확히 반대 방향의 압력을 만든다.

- **검색 쪽 압력은 「작게」다.** 임베딩은 청크 전체를 벡터 하나로 압축한다. 청크에 주제가 여러 개 섞여 있으면 그 벡터는 여러 주제의 평균이 되어 어느 쪽과도 뚜렷하게 가깝지 않게 된다. 환불·교환·배송이 한 덩어리에 있으면 「환불은 며칠까지?」와의 유사도가 희석된다.
- **생성 쪽 압력은 「크게」다.** 모델은 청크 밖을 볼 수 없다. 「14일 이내」와 「단, 미개봉 상품에 한한다」가 다른 청크로 갈라지고 한쪽만 검색되면, 모델은 조건을 절반만 아는 채로 답한다. 문장 단위로 잘게 자를수록 이 사고가 늘어난다.

그래서 실무의 출발점은 **문단 경계로 자르고 수백 토큰 안팎에서 시작해 조정**하는 것이며(s11의 「청킹」 줄이 이 문장을 한 줄로 줄인 것이다), 갈라짐 사고는 **오버랩(overlap)** 으로 완화한다.

**오버랩이 왜 필요한가 — 잘리는 자리를 눈으로 보기.** 오버랩은 뒤 청크가 앞 청크의 끝부분을 다시 포함하도록 겹쳐 자르는 것이다. 경계가 어디에 떨어지든 **문맥이 한쪽에는 온전히 남게** 만드는 보험이다.

```
원문
  ... 환불은 구매일로부터 14일 이내에 신청할 수 있습니다. 단, 미개봉 상품에 한합니다. ...

[오버랩 없음]  경계가 두 문장 사이에 떨어진 경우
  청크 A : "... 환불은 구매일로부터 14일 이내에 신청할 수 있습니다."
  청크 B : "단, 미개봉 상품에 한합니다. ..."
  → 질문 "환불 며칠까지?" 는 A만 끌어온다   ⇒ 답변에서 '미개봉' 조건이 통째로 빠진다
  → 질문 "미개봉만 되나요?" 는 B만 끌어온다 ⇒ 무엇이 미개봉 조건인지 알 수 없다

[오버랩 있음]  뒤 청크가 앞 문장 하나를 다시 품는다 (예: 청크의 10~20%)
  청크 A : "... 환불은 구매일로부터 14일 이내에 신청할 수 있습니다."
  청크 B : "환불은 구매일로부터 14일 이내에 신청할 수 있습니다. 단, 미개봉 상품에 한합니다. ..."
  → 어느 쪽이 검색되어도 '14일'과 '미개봉'이 함께 따라온다

  대가: 저장 용량과 임베딩 비용이 겹친 비율만큼 늘고, 같은 내용이 top-k 자리를
        두 번 차지해 다양성이 줄 수 있다. 그래서 무한정 겹치지 않고 10~20% 선에서 잡는다.
```

**구체 사례.** 세 가지 대표 전략의 성격은 이렇다.

| 방식 | 어떻게 자르나 | 장점 | 단점 | 잘 맞는 문서 |
|---|---|---|---|---|
| 고정 크기 | 토큰·문자 수를 세어 N토큰마다 기계적으로 자른다(보통 오버랩과 함께) | 구현이 가장 단순하다. 청크 길이가 균일해 비용·성능 예측이 쉽다 | 문장·표·코드 한가운데를 자른다. 의미 경계를 전혀 보지 않는다 | 형식이 일정하지 않은 잡다한 텍스트, 로그, 자막 |
| 문단 경계 | 빈 줄·문단·문장 단위로 자르되, 목표 크기를 넘으면 다음 경계에서 끊는다 | 의미 단위를 보존하면서 길이도 어느 정도 통제된다. **대부분의 문서에서 기본값** | 문단 길이가 들쭉날쭉하면 청크 길이도 들쭉날쭉해진다 | 정책·매뉴얼·FAQ·블로그 등 사람이 쓴 산문 대부분 |
| 의미 기반 | 인접 문장의 임베딩 유사도가 크게 떨어지는 지점(주제가 바뀌는 자리)을 찾아 자른다 | 주제 단위가 정확히 떨어져 검색 정밀도가 가장 높을 수 있다 | 색인 시점에 임베딩을 한 번 더 돌려야 해 비용·시간이 든다. 임계값 튜닝이 필요하다 | 주제가 자주 바뀌는 긴 문서, 회의록, 인터뷰 전사 |
| (참고) 구조 기반 | 제목 계층(H1/H2/H3)이나 표·조항 번호를 그대로 경계로 삼고, 각 청크 앞에 상위 제목을 붙여 둔다 | 「어느 장의 이야기인지」가 청크 안에 남아 검색·생성 모두 유리하다 | 구조 정보가 없는 문서에는 아예 쓸 수 없다 | 사규·약관·API 문서·마크다운 위키 |

고르는 순서를 하나만 정한다면 이렇다 — **구조가 있으면 구조 기반, 없으면 문단 경계 + 오버랩으로 시작하고, 검색 지표(10절)가 잘 나오지 않을 때만 의미 기반이나 크기 조정으로 넘어간다.** 청킹은 손대는 순간 전체 재색인이 필요하므로, 근거 없이 자주 바꾸기에는 비싼 조절 항목이다.

**인용.** 청킹은 아직 하나의 정설로 수렴한 주제가 아니며, 표준 크기를 규정한 대표 논문도 없다. 다만 「검색 단위를 문서 전체가 아니라 구절(passage)로 잡는다」는 발상 자체는 정보 검색에서 오래된 것이고, 오늘날 RAG 문맥에서 표준이 된 것은 Karpukhin, V. et al., *Dense Passage Retrieval for Open-Domain Question Answering*, EMNLP 2020(arXiv:2004.04906) 이후다. 「청크가 잘려 조건이 유실된다」는 실패는 9절에서 인용하는 Barnett et al.(2024)이 현장 사례로 보고했다. 크기와 오버랩 비율은 문서 유형별로 실측해 정하는 것이 옳다.

**대응 슬라이드: s11**

## 5. 검색 — 완전 탐색, 근사 최근접 이웃, 그리고 키워드와의 하이브리드

**정의.** 검색은 질의 벡터와 가장 가까운 청크 top-k개를 인덱스에서 꺼내오는 단계다. 후보 전부와 유사도를 계산하는 방식을 **완전 탐색(brute-force search)**, 정확도를 조금 내주고 훨씬 적은 비교로 근사 답을 얻는 방식을 **ANN(근사 최근접 이웃, approximate nearest neighbor)** 이라 한다.

**원리(왜 근사로 가야 하는가).** 완전 탐색의 비용은 단순하다. 청크가 N개이고 벡터 차원이 d라면, 질의 한 건마다 **N × d 번의 곱셈·덧셈**이 필요하다. 숫자를 넣어 보면 감이 온다.

```
  N = 1,000,000 청크,  d = 1,024 차원
    질의 1건  →  1,000,000 × 1,024 ≈ 10억 회 연산
    초당 100건 →  약 1,000억 회/초

  거기에 벡터 자체의 메모리도 든다:
    1,000,000 × 1,024 × 4바이트(float32) ≈ 4.1 GB
```

한 건이라면 몇백 밀리초로 버틸 수 있지만, 동시 사용자가 붙고 인덱스가 수천만 건으로 커지면 곧 무너진다. ANN은 **「1등을 반드시 맞힌다」는 보장을 내려놓는 대신 비교 횟수를 줄인다.** 대표적인 세 갈래는 성격이 다르다.

- **그래프 기반(HNSW)** — 벡터들을 이웃끼리 연결한 다층 그래프로 만들어, 성긴 위층에서 대충 방향을 잡고 촘촘한 아래층으로 내려가며 가까워지는 방향으로만 이동한다. 전체를 보지 않고 경로를 따라 수백 개만 비교한다.
- **군집 기반(IVF)** — 벡터를 미리 군집으로 나누고, 질의와 가까운 몇 개 군집만 뒤진다. 정답이 뒤지지 않은 군집에 있으면 놓친다.
- **압축 기반(PQ)** — 벡터를 짧은 코드로 양자화해 메모리와 비교 비용을 줄인다. 정밀도를 잃는 대신 훨씬 큰 인덱스를 메모리에 올릴 수 있다.

세 갈래 모두 **정확도(재현율)와 속도·메모리를 맞바꾸는 조절 항목**을 노출한다. 여기서 잃은 재현율은 검색 지표(10절)로 측정해야 하며, 「빨라졌는데 답이 나빠졌다」의 상당수가 이 조절 항목을 재지 않고 조인 결과다.

**벡터 검색만으로는 왜 부족한가.** 임베딩은 의미를 뭉뚱그리는 데 능한 대신 **정확한 문자열을 무디게 만든다.** 「policy-04」·「XR-7 모델」·사람 이름·법 조항 번호처럼 **한 글자만 달라도 다른 것**을 가리키는 토큰은, 의미 공간에서 서로 아주 가까운 자리에 뭉쳐 놓인다(둘 다 「제품 코드처럼 생긴 것」이다). 반대로 키워드 검색(BM25)은 그런 토큰을 정확히 집어내지만, 「환불」로 색인된 문서를 「반품」으로 물으면 하나도 찾지 못한다. 두 방식은 **서로의 약점을 정확히 보완**하므로, 실무의 기본형은 둘을 함께 돌려 순위를 합치는 **하이브리드 검색(hybrid search)** 이다.

| 방식 | 무엇을 기준으로 매기나 | 강점 | 약점 | 고유명사·제품 코드 | 오타 |
|---|---|---|---|---|---|
| 벡터 검색 | 질의와 청크 임베딩의 코사인 유사도 | 표현이 달라도(동의어·의역·질문형 ↔ 서술형) 잡는다. 언어를 넘나드는 검색도 가능 | 정확 일치를 보장하지 않는다. 왜 그 문서가 나왔는지 설명하기 어렵다 | **약하다.** 「XR-7」과 「XR-9」가 벡터 공간에서 거의 같은 자리에 놓인다 | **BM25보다는 낫다.** 서브워드 일부가 살아남아 완전히 놓치지는 않지만, 질의 오타는 밀집 검색에서도 알려진 약점이다 |
| 키워드 검색 | 질의 단어의 문서 내 빈도와 희소성, 문서 길이 보정(BM25 계열의 랭킹 함수) | 정확 일치에 강하다. 점수 근거가 투명하고 인덱스가 가볍다 | 동의어·의역을 전혀 못 잡는다. 어휘가 겹치지 않으면 0점이다 | **강하다.** 희소한 토큰일수록 가중치가 커져 오히려 정확히 집어낸다 | **약하다.** 글자 하나만 틀려도 다른 토큰이 되어 완전히 놓친다 |
| 하이브리드 | 두 검색의 순위를 융합하거나(예: RRF) 점수를 가중 합산 | 의미와 정확 일치를 동시에 잡는다. 한쪽이 실패해도 다른 쪽이 건진다 | 인덱스를 둘 유지해야 하고, 융합 가중치라는 조절 항목이 하나 더 생긴다 | 벡터가 놓쳐도 BM25가 건진다 | BM25가 놓쳐도 벡터가 건진다 |

순위 융합에 흔히 쓰이는 **RRF(Reciprocal Rank Fusion, 상호 순위 융합)** 는 발상이 단순하다. 각 검색기에서 문서의 **점수가 아니라 순위**만 가져와 `1/(c + 순위)` 를 더한다(c는 상수이며 흔히 60을 쓴다. 앞의 top-k와는 무관한 값이다). 점수 척도가 서로 다른 두 검색기(코사인 0~1과 BM25의 무한정 양수)를 정규화 없이 합칠 수 있다는 것이 장점이다.

**메타데이터 필터링(metadata filtering).** 유사도 이전에 **후보 집합 자체를 좁히는** 장치다. 「부서 = 고객지원」, 「유효일자 ≥ 오늘」, 「접근 권한 ⊇ 요청자」 같은 조건으로 거른다. 여기서 중요한 것은 **거르는 시점**이다.

- **사전 필터링(pre-filter)** — 조건을 만족하는 청크만 후보로 두고 그 안에서 검색한다. top-k가 언제나 조건을 만족하고, 권한 누수를 원천 차단한다. 다만 인덱스가 이 필터를 지원해야 하고, 조건이 아주 좁으면 ANN이 뒤질 그래프·군집이 성겨져 재현율이 떨어질 수 있다.
- **사후 필터링(post-filter)** — 먼저 top-k를 뽑고 나서 조건에 안 맞는 것을 버린다. 구현이 쉽지만, 조건에 안 맞는 문서가 상위를 다 차지하면 **남는 근거가 0건**이 될 수 있다. 권한처럼 안전에 관계된 조건은 **사후 필터링으로 처리하면 안 된다** — 이미 검색 결과로 존재했다는 사실 자체가 위험하다.

**구체 사례.** s11의 `top-k` 줄이 정확히 이 절의 조절 항목이다 — 적게 잡으면 정답 문서를 놓치고(재현율↓), 많이 잡으면 잡음과 비용이 올라간다. 처방은 「넉넉히 뽑고 리랭킹으로 정제」다. 넉넉히 뽑아도 되는 이유, 그리고 뽑은 뒤 무엇으로 정제하는지가 다음 절이다.

**인용.**
- Robertson, S., Zaragoza, H., *The Probabilistic Relevance Framework: BM25 and Beyond*, Foundations and Trends in Information Retrieval 3(4), 2009 — BM25 계열 랭킹 함수의 확률적 근거와 변형을 정리한 표준 참고 문헌.
- Karpukhin, V. et al., *Dense Passage Retrieval for Open-Domain Question Answering*, EMNLP 2020(arXiv:2004.04906) — 질문과 구절을 각각 인코딩해 밀집 벡터로 검색하는 방식이 BM25를 능가할 수 있음을 보인 연구. 오늘날 벡터 검색 기반 RAG의 직접적 조상이다.
- Malkov, Y. A., Yashunin, D. A., *Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs*, IEEE TPAMI 42(4), 2020(arXiv:1603.09320) — 오늘날 벡터 저장소의 사실상 기본 인덱스가 된 HNSW를 제안한 논문.
- Cormack, G. V., Clarke, C. L. A., Büttcher, S., *Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods*, SIGIR 2009 — 점수 대신 순위만으로 여러 검색 결과를 결합하는 단순한 방법이 정교한 학습 기반 결합보다 나을 수 있음을 보였다.

**대응 슬라이드: s10–s11**

## 6. 리랭킹 — 싼 것으로 넓게, 비싼 것으로 좁게

**정의.** **리랭킹(reranking)** 은 1차 검색이 뽑아 온 후보들을 더 정밀한 모델로 다시 채점해 순서를 바로잡는 단계다. 1차 검색이 쓰는 모델을 **bi-encoder(이중 인코더)**, 리랭킹이 쓰는 모델을 **cross-encoder(교차 인코더)** 라 부른다.

**원리(왜 정확하고, 왜 비싼가).** 두 구조의 차이는 **질문과 문서가 서로를 보느냐**다.

```
[bi-encoder — 이중 인코더]  질문과 문서를 따로따로 인코딩한다

    질문 ──►┌───────────┐──► q 벡터 ─┐
            │   인코더  │            ├──► 코사인 유사도 = 점수
    문서 ──►│  (같은 것)│──► d 벡터 ─┘
            └───────────┘
      └ d 벡터는 색인 시점에 미리 계산해 저장해 둔다. 질의 시점에는 벡터 비교만
        하면 되므로 100만 건도 밀리초 단위다. 대신 질문과 문서가 서로를 보지
        못한 채 각자 하나의 벡터로 압축된다 — 그 압축에서 정보가 깎인다.

[cross-encoder — 교차 인코더]  질문과 문서를 이어붙여 함께 인코딩한다

    [질문 ⧺ 문서] ──►┌───────────┐──► 관련도 점수 하나
                     │   인코더  │
                     └───────────┘
      └ 두 텍스트의 토큰이 서로 어텐션한다 → 질문의 "며칠"이 문서의 "14일"에
        대응되는지까지 본다. 대신 (질문, 문서) 쌍마다 모델을 한 번씩 돌려야
        하므로 미리 계산해 둘 수 없다 — 후보 수에 비례해 비용이 든다.

[2단 구조]  싼 것으로 넓게 → 비싼 것으로 좁게

   100만 청크 ──bi-encoder(ANN)──► 후보 50개 ──cross-encoder──► 상위 5개 ──► 프롬프트
               (밀리초, 대략)                  (수십 회 호출)      (정밀)
```

이중 인코더가 정보를 잃는 지점은 **압축의 시점**이다. 문서를 벡터로 만들 때는 어떤 질문이 올지 모르므로, 문서의 모든 측면을 하나의 벡터에 평균해 담을 수밖에 없다. 「환불 기한·환불 조건·환불 절차」가 섞인 청크는 그 셋의 평균 방향을 갖게 되고, 「기한」만 묻는 질문과의 각도가 실제 관련도보다 벌어진다. 교차 인코더는 질문이 도착한 뒤에 계산하므로 이 평균화를 겪지 않는다 — PART 1 5절에서 본 어텐션이 **두 텍스트를 가로질러** 작동하기 때문에, 질문의 「며칠」이 문서의 「14일」을 직접 가리키는 관계까지 계산에 들어간다.

그래서 **왜 top-k를 넉넉히 뽑는가**에 답이 나온다. 1차 검색의 임무는 「1등을 맞히는 것」이 아니라 **「정답을 후보 안에 넣어 두는 것」** 이다. 정답이 12위여도 후보 50개 안에 있으면 리랭킹이 1위로 끌어올릴 수 있지만, 후보 5개만 뽑아 정답이 밖에 있었다면 뒤에서 무엇을 해도 복구되지 않는다. 이것이 10절에서 **검색은 재현율(recall@k)로, 리랭킹은 순위 품질(MRR·nDCG)로** 나눠 재는 이유다.

k를 무한정 키우지 못하는 이유도 분명하다. 교차 인코더 호출 수가 k에 비례해 지연과 비용이 늘고, 리랭킹 없이 그대로 프롬프트에 넣는다면 잡음이 늘고 컨텍스트 윈도우를 잡아먹으며, 근거가 창 가운데 묻혀 무시되는 lost-in-the-middle(PART 1 4절)에 걸린다. 실무의 기본형은 **1차 top-k를 수십 개, 리랭킹 후 상위 3~5개만 프롬프트에 넣기**다.

**구체 사례.** s11의 `리랭킹` 줄이 말하는 「가져온 것 중 진짜 관련된 걸 위로」가 이 절의 내용이다 — 벡터 검색 상위를 그대로 믿지 말고 관련도를 다시 매기라는 뜻이다. 2절의 표로 돌아가 보면 이 단계가 무엇을 하는지 구체적으로 보인다. 「교환은 수령 후 7일 이내」는 환불 질문과의 코사인 유사도가 0.71로 2순위에 올라와 있지만, 실제로는 **환불 기한을 묻는 질문의 답이 아니다.** 교차 인코더는 질문의 「환불」과 문서의 「교환」이 다른 절차를 가리킨다는 것을 두 텍스트를 함께 읽고 판정할 수 있어, 이 문서를 아래로 내린다. 이중 인코더가 「같은 주제 영역」까지만 구별한다면, 교차 인코더는 **「이 질문의 답인가」** 를 구별한다.

**인용.**
- Nogueira, R., Cho, K., *Passage Re-ranking with BERT*, 2019(arXiv:1901.04085) — 1차 검색 결과를 BERT 기반 교차 인코더로 재채점하면 검색 품질이 크게 오른다는 것을 보인 대표 연구. 오늘날 RAG의 리랭킹 단계가 이 계열에 뿌리를 둔다.
- Reimers & Gurevych(2019, 2절 인용) — 이중 인코더와 교차 인코더의 정확도·속도 트레이드오프를 명시적으로 대비하고, 대규모 검색에 이중 인코더가 필요한 이유를 정리했다.

**대응 슬라이드: s11**

## 7. 증강 — 컨텍스트를 조립하는 순서

**정의.** 증강은 검색해 온 청크를 프롬프트 안에 배치해 「근거가 박힌 프롬프트」를 조립하는 단계다. 이 단계에서 결정되는 것은 세 가지다 — **무엇을 넣을지, 어떤 순서로 넣을지, 각 조각에 어떤 표시를 붙일지.**

**원리(왜 지시 → 근거 → 질문 순서인가).** 세 요소의 배치 순서는 취향이 아니라 PART 1에서 본 두 성질에서 따라 나온다.

**첫째, 지시가 근거보다 앞에 와야 한다.** 모델은 텍스트를 앞에서부터 읽으며 다음 토큰을 계산한다. 근거 문서를 먼저 던지면 모델은 그것을 「무엇을 위한 자료인지 모르는 상태」로 통과시킨다. 지시를 먼저 두면 이후의 모든 토큰이 그 지시를 조건으로 해석된다 — 「이 문서들에서 답을 찾아라」를 읽은 뒤에 문서를 읽는 것과, 문서를 다 읽고 나서 그 요구를 받는 것은 다르다.

**둘째, 질문은 근거 뒤에 와야 한다.** 근거 문서는 대개 프롬프트에서 가장 긴 덩어리다. 질문을 그 앞에 두면 질문과 생성 시작점 사이에 수천 토큰이 끼어들어, lost-in-the-middle의 「가운데」에 정확히 놓인다. 질문을 근거 바로 뒤, 즉 **생성 시작점 바로 앞**에 두면 가장 주목받는 자리를 차지한다.

**셋째, 핵심 지시는 맨 끝에 한 번 더 반복한다.** 프롬프트의 앞과 뒤가 모두 주목도가 높은 자리이므로, 가장 어겨서는 안 되는 규칙(「없으면 없다고 답하라」)을 양쪽에 둔다.

근거 문서 **내부**의 순서에도 규칙이 있다. 리랭킹으로 매긴 순위를 그대로 위에서 아래로 늘어놓으면 가장 관련도 높은 문서가 긴 블록의 맨 앞에 오고, 그다음으로 중요한 문서들이 「가운데」에 묻힌다. 그래서 관련도 상위 문서를 **블록의 앞과 뒤로 나눠 배치**하는 방식이 자주 쓰인다. 그리고 청크마다 **문서 id·제목·유효일자를 함께 적어 둔다** — 8절의 출처 표기가 가능하려면 모델이 그 id를 볼 수 있어야 하고, 유효일자는 상충하는 근거를 만났을 때 무엇을 따를지 판단하는 재료가 된다.

**구체 사례 — 프롬프트 템플릿 전문.** 아래는 s10 데모의 환불 정책 질문을 실제 서비스에 넣는다면 최소선이 될 프롬프트다. 각 블록이 위의 원리 중 무엇을 반영했는지는 블록 제목만 따라 읽어도 드러난다.

```text
# 역할
너는 사내 정책 안내 어시스턴트다. 아래 [근거 문서]에 적힌 내용만을 사실 근거로 사용한다.

# 규칙
1. 답변의 모든 사실 문장은 [근거 문서] 중 하나에서 확인할 수 있어야 한다.
2. 근거 문서에서 확인할 수 없는 내용은 쓰지 않는다. 답하는 데 필요한 정보가 없으면
   "제공된 문서에서 확인할 수 없습니다"라고 답하고, 무엇이 없는지 한 줄로 밝힌다.
3. 사실 문장 끝에는 근거가 된 문서 id를 [policy-04] 형태로 붙인다.
   여러 문서가 필요하면 [policy-04][policy-07]처럼 나열한다.
4. [근거 문서]에 없는 id를 새로 만들어 붙이지 않는다.
5. 근거 문서끼리 내용이 충돌하면 updated 값이 더 최근인 문서를 따르고,
   충돌이 있었다는 사실을 마지막에 한 줄로 밝힌다.
6. 추측·일반 통념·너의 사전 지식으로 빈칸을 메우지 않는다.

# 근거 문서
<doc id="policy-04" title="환불 규정" updated="2026-05-01">
환불은 구매일로부터 14일 이내에 신청할 수 있습니다. 단, 미개봉 상품에 한합니다.
</doc>

<doc id="policy-07" title="교환 규정" updated="2026-03-12">
교환은 상품 수령 후 7일 이내에 신청하세요. 단순 변심의 경우 왕복 배송비는 고객이 부담합니다.
</doc>

# 질문
우리 회사 환불 정책은 며칠까지 가능해?

# 출력 형식
- 첫 줄  : 질문에 대한 한 문장 요약 답변
- 그다음 : 적용되는 세부 조건을 불릿으로. 각 불릿 끝에 문서 id를 표기한다.
- 마지막 : "참고 문서: " 뒤에 실제로 사용한 id를 모두 나열한다.

# 다시 한번
[근거 문서]에 없는 내용은 쓰지 않는다. 없으면 "제공된 문서에서 확인할 수 없습니다"라고 답한다.
```

이 템플릿에서 눈여겨볼 세 가지. **① 규칙 2가 부정형과 긍정형을 짝지었다** — 「쓰지 않는다」로 끝내지 않고 「이렇게 답하라」는 대체 행동을 줬다(PART 1 9절). **② 근거 문서를 `<doc>` 태그로 감쌌다** — 어디서 어디까지가 근거인지 경계가 분명해야 모델이 자기 지식과 섞지 않고, 프롬프트 주입 시도를 걸러 내기도 쉽다. **③ 「다시 한번」 블록이 규칙 2를 반복한다** — 근거 문서가 길어질수록 이 반복의 효과가 커진다.

**인용.** Liu, N. F. et al., *Lost in the Middle: How Language Models Use Long Contexts*, Transactions of the ACL, 2024(arXiv:2307.03172) — 긴 문맥에서 정답의 위치에 따라 성능이 U자 형태로 달라짐을 보인 연구. 근거 문서를 몇 개까지 넣을지, 그것을 어느 자리에 놓을지가 왜 성능 문제인지의 직접적 근거다.

**대응 슬라이드: s10**

## 8. 생성과 출처 표기 — 근거 없는 문장을 막는 법

**정의.** 답변의 모든 사실 문장이 제공된 근거로 뒷받침되는 성질을 **근거성**이라 하고, 각 문장이 어느 문서에서 왔는지 답변에 함께 표기하는 것을 **출처 표기(citation)** 라 한다. 이 성질이 깨진 상태가 9절 카탈로그의 「근거 무시」이고, 그것을 수치로 재는 것이 10절의 faithfulness다.

**원리(근거를 줬는데 왜 안 쓰는가).** 모델에게 근거 문서는 「반드시 따라야 할 정답」이 아니라 **그냥 문맥의 일부**다. 자기 파라메트릭 지식과 창 안의 문서가 충돌할 때 어느 쪽이 이길지는 확률이 정하며, 학습 말뭉치에서 반복적으로 본 통념(「환불은 보통 30일」)이 낯선 사내 문서 한 조각보다 강할 수 있다. **어느 쪽을 따를지는 지시가 정해야 한다.** 이것이 9절 「근거 무시」의 정체이고, 7절 템플릿의 규칙 1·6이 존재하는 이유다.

출처 표기는 여기에 두 가지를 더한다. 첫째, **사람이 검증할 수 있게** 만든다 — id가 붙어 있으면 원문을 열어 대조하는 데 몇 초면 된다. 둘째, 그 자체로 **근거 없는 문장을 억제**한다. 모든 사실 문장에 id를 달라고 요구하면, 근거 없는 문장을 쓰려면 id를 지어내야 하고, 지어낸 id는 다음의 형식 검증에서 걸린다.

**근거 없는 문장을 막는 지시문.** 효과가 좋은 순서로 정리하면 이렇다. 공통 원리는 PART 1 9절과 같다 — **금지에는 반드시 대체 행동을 짝지운다.**

| 지시 유형 | 문구 예 | 무엇을 막나 |
|---|---|---|
| 근거 한정 | 「아래 [근거 문서]에 적힌 내용만을 사실 근거로 사용한다」 | 내부 지식이 근거를 이기는 것 |
| 빈칸 처리 규칙 | 「확인할 수 없으면 '제공된 문서에서 확인할 수 없습니다'라고 답하고 무엇이 없는지 밝힌다」 | 모른다고 말하지 못해 지어내는 것 |
| 문장 단위 출처 | 「모든 사실 문장 끝에 근거 문서 id를 [policy-04] 형태로 붙인다」 | 근거와 추측이 한 문단에 섞이는 것 |
| id 조작 금지 | 「[근거 문서]에 없는 id를 새로 만들어 붙이지 않는다」 | 형식만 그럴듯한 가짜 출처 |
| 충돌 처리 규칙 | 「충돌하면 updated가 최근인 문서를 따르고 충돌 사실을 밝힌다」 | 구·신 버전이 섞여 호출마다 답이 달라지는 것 |
| 범위 밖 처리 | 「질문이 정책 범위를 벗어나면 답하지 말고 담당 창구를 안내한다」 | 엉뚱한 근거를 억지로 끌어다 쓰는 것 |

**구체 사례 — id를 답변에 달게 하고, 그것을 검증하기.** 출처를 자연어 문장 안에 섞어 두면 검증을 사람이 눈으로 해야 한다. 구조화 출력(PART 1 10절)으로 받으면 **코드가 검증할 수 있다.**

```json
{
  "answer": "환불은 구매일로부터 14일 이내에 신청할 수 있으며, 미개봉 상품에 한합니다.",
  "claims": [
    { "text": "환불 신청 기한은 구매일로부터 14일 이내다.", "doc_id": "policy-04" },
    { "text": "환불 대상은 미개봉 상품에 한한다.",           "doc_id": "policy-04" }
  ],
  "cited": ["policy-04"],
  "unsupported": false
}
```

이 형태를 받으면 검증이 세 단계로 갈린다. 앞의 두 단계는 근거 원문을 다시 읽지 않으므로 싸고, 그중 1단계는 비용이 아예 0이라 **항상 켜 두는 것이 맞다.**

1. **형식 검증 — 코드로, 비용 0.** `claims[].doc_id` 가 전부 이번 호출에 실제로 넣은 청크 id 집합에 들어 있는가. 집합 포함 여부만 보면 되므로 판정이 결정적이다. 없는 id가 하나라도 있으면 그 답변은 신뢰할 수 없다. 존재하지 않는 문서 id를 만들어 내는 것은 **출처 형식을 흉내 낸 환각**이며, 이 검증이 없으면 형식만 그럴듯한 답변이 그대로 사용자에게 나간다 — 이 절 인용의 Gao et al.(2023)이 「인용이 달려 있다」와 「인용이 옳다」를 갈라 다루는 이유가 여기에 있다.
2. **커버리지 점검 — 값싼 휴리스틱 신호.** `answer` 의 문장 수와 `claims` 수를 대조한다. 문장을 세는 일까지는 코드로 공짜지만, 그 뒤가 결정적이지 않다 — 「어느 문장이 사실 문장인가」(인사말·요약 문장은 근거가 필요 없다)와 「이 문장이 저 claim으로 뒷받침되는가」는 의미 대조가 필요한 판단이고, 그것은 3단계의 일이다. 그래서 이 단계는 합격/불합격 판정이 아니라 **「claim보다 문장이 눈에 띄게 많다」는 경보**로 쓴다. 근거 없이 채워 넣은 자리가 있을 가능성을 가리킬 뿐이고, 확인은 3단계나 사람이 한다.
3. **근거 검증 — 모델 또는 사람, 비용 있음.** 각 `claims[].text` 가 해당 청크 본문에서 **실제로 도출되는가**. id는 맞는데 그 문서가 그런 말을 하지 않는 경우가 여기서 걸린다. 이 검증을 지표로 정량화한 것이 10절의 faithfulness다.

세 단계의 순서에는 이유가 있다. **1과 2는 근거 원문을 다시 읽지 않고도 계산되므로 실시간 요청 경로에 넣을 수 있고**, 3은 별도 호출이 필요하므로 표본 검사나 평가 실행에서 돌린다. 다만 둘의 처리 방식은 다르다. **1에서 걸린 응답은 결정적으로 틀린 것**이므로 사용자에게 그대로 보내지 말고, 재요청하거나 「확인할 수 없습니다」로 대체한 뒤 원문을 로그에 남긴다. **2가 울린 응답은 차단 대상이 아니라 표본**이다 — 3단계 검증이나 사람 검수로 넘겨 실제로 근거 없는 문장이 있었는지 확인한다.

**인용.** Gao, T., Yen, H., Yu, J., Chen, D., *Enabling Large Language Models to Generate Text with Citations*, EMNLP 2023(arXiv:2305.14627) — 모델이 답변에 출처를 붙이도록 만들고, 그 인용이 실제로 문장을 뒷받침하는지를 자동으로 평가하는 틀을 제시한 연구. 「인용이 달려 있다」와 「인용이 옳다」가 별개의 문제라는 점을 정면으로 다룬다.

**대응 슬라이드: s10 · s12**

## 9. RAG 실패 유형 카탈로그

**정의.** RAG는 단일 모델이 아니라 여덟 단계짜리 파이프라인이므로, 「답이 틀렸다」는 관찰만으로는 아무것도 고칠 수 없다. **어느 단계가 깨졌는지 나누는 것**이 진단의 전부다.

**원리(왜 단계로 나눠야 하는가).** 같은 증상이 전혀 다른 원인에서 나온다. 「모른다고 답한다」는 증상은 정답 문서가 애초에 색인에 없어서일 수도, 색인에는 있지만 검색되지 않아서일 수도, 검색은 됐지만 순위가 낮아 잘려서일 수도, 다 들어갔는데 모델이 안 써서일 수도 있다. **네 원인의 처방은 전부 다르다.** 그래서 진단은 언제나 이 순서의 사다리를 위에서부터 내려가며 한다.

1. **정답 청크가 인덱스에 존재하는가?** — 없으면 로드·청킹 문제다. 검색을 아무리 손봐도 소용없다.
2. **그 청크가 top-k 안에 들어왔는가?** — 안 들어왔으면 청킹 크기·임베딩 모델·k·하이브리드 검색의 문제다(10절의 recall@k).
3. **상위 몇 등 안에 들어왔는가?** — 후보에는 있는데 아래에 있으면 리랭킹의 문제다(MRR·nDCG).
4. **프롬프트에 들어간 근거를 답이 실제로 썼는가?** — 안 썼으면 지시·순서·컨텍스트 과적재의 문제다(faithfulness).

**구체 사례.** 앞의 네 유형은 s12 데모가 그대로 보여주는 것이고, 뒤의 일곱은 현장에서 자주 마주치는 것들이다.

| 실패 유형 | 증상 | 원인 | 처방 |
|---|---|---|---|
| 검색 실패(retrieval miss) | 문서에 답이 있는데도 "모른다"고 답한다 | 청크가 너무 커서 핵심 문장이 묻히거나, top-k가 모자라 정답 문서가 잘렸다 | 청크를 줄이고 오버랩을 주기 · top-k를 넉넉히 뽑고 리랭킹으로 정제 |
| 잡음 유입(noise) | 엉뚱한 문서를 근거로 들며 자신 있게 틀린다 | 유사도만으로 뽑아 주제가 다른 청크가 상위에 섞였다 | 메타데이터 필터로 후보를 좁히고, 리랭킹으로 상위를 다시 정렬한다 |
| 근거 무시(groundedness) | 근거를 줬는데도 모델이 제 기억으로 답한다 | 프롬프트가 근거 사용을 강제하지 않아 내부 지식이 이긴다 | "제공된 문서만 근거로 쓰고 없으면 없다고 답하라" + 출처 표기 요구 |
| 최신성 실패(staleness) | 이미 바뀐 옛 정책을 근거로 답한다 | 원본이 바뀌었는데 색인이 따라가지 못했다 | 문서 변경 시 재색인 · 문서에 유효일자 메타데이터를 붙여 필터링 |
| 색인 누락(ingestion gap) | 특정 문서가 어떤 질문에도 한 번도 검색되지 않는다 | 로더가 스캔 PDF·표·이미지를 읽지 못해 본문이 애초에 인덱스에 없다 | 로드 산출물을 표본 검수 · OCR·표 파서 추가 · 문서 대비 청크 수 대조 |
| 문맥 절단(chunk truncation) | 조건의 절반만 반영된다("14일"은 맞는데 "미개봉"이 빠진다) | 답이 두 청크에 걸쳐 있고 한쪽만 검색됐다 | 문단 경계로 자르고 오버랩 주기 · 검색된 청크의 인접 청크를 함께 가져오기 |
| 질의 불일치(query mismatch) | "그건 언제까지야?"처럼 짧거나 대명사가 섞인 질문에서만 실패한다 | 질의가 짧아 벡터가 뭉뚱그려지고, 앞선 대화 맥락이 질의에 반영되지 않았다 | 대화 이력을 반영해 질의를 완전한 문장으로 재작성 · 하이브리드 검색으로 보강 |
| 상충 근거(conflicting evidence) | 같은 항목을 물을 때마다 다른 숫자를 답한다 | 구버전과 신버전 문서가 함께 검색됐는데 우선순위 규칙이 없다 | 유효일자·버전 메타데이터로 최신본 우선 · 충돌 시 처리 규칙을 프롬프트에 명시 |
| 컨텍스트 과적재(context overload) | top-k를 늘렸더니 오히려 정확도가 떨어졌다 | 근거가 창 가운데 묻혀 주목받지 못한다(lost-in-the-middle) | 리랭킹 후 상위 소수만 넣기 · 관련도 높은 청크를 블록의 앞뒤 가장자리에 배치 |
| 인용 조작(citation fabrication) | 답변에 붙은 문서 id가 실제로 존재하지 않는다 | 출처 형식만 흉내 내 그럴듯한 id를 생성했다 | 제공한 청크 id 집합과 대조하는 형식 검증을 코드로 강제 · 실패 시 재요청 |
| 권한 누수(access leakage) | 볼 권한이 없는 문서 내용이 답변에 섞여 나온다 | 인덱스가 권한 구분 없이 만들어졌거나 필터가 검색 '뒤에' 적용됐다 | 청크에 권한 메타데이터를 붙이고 검색 '이전에' 거른다(사전 필터링) |

열한 유형을 사다리에 얹으면 이렇게 갈린다 — **색인 누락**은 (1)단계, **검색 실패·문맥 절단·질의 불일치**는 (2)단계, **잡음 유입·상충 근거**는 (3)단계, **근거 무시·컨텍스트 과적재·인용 조작**은 (4)단계다. **최신성 실패**는 색인 갱신 주기의 문제라 사다리 밖에 있고, **권한 누수**는 품질이 아니라 안전 문제라 별도로 다뤄야 한다 — 다른 실패는 답이 나빠지는 데 그치지만, 이것은 그 자체로 사고다.

**인용.**
- Barnett, S. et al., *Seven Failure Points When Engineering a Retrieval Augmented Generation System*, 2024(arXiv:2401.05856) — 실제 RAG 시스템 구축 사례들에서 반복적으로 관찰된 실패 지점을 파이프라인 단계별로 정리한 경험 연구. 게재처는 확인하지 않았으므로 저자·제목·연도만 밝힌다.
- Liu et al.(2024, 7절 인용) — 컨텍스트 과적재 항목의 직접적 근거.

**대응 슬라이드: s12**

## 10. RAG 평가 — 검색과 생성을 나눠 재기

**정의.** RAG 평가는 두 층으로 나뉜다. **검색 지표**는 「필요한 근거를 가져왔는가」를, **생성 지표**는 「가져온 근거로 제대로 답했는가」를 잰다. 최종 답변 하나만 채점하는 것으로는 이 둘을 구별할 수 없다.

**원리(왜 나눠 재야 하는가).** 최종 정답률만 보면 「70점」이라는 숫자는 얻지만 **무엇을 고쳐야 하는지는 알 수 없다.** 검색이 정답 문서를 못 가져와서 70점인 경우와, 다 가져왔는데 모델이 안 써서 70점인 경우는 처방이 정반대다. 앞의 경우 프롬프트를 아무리 다듬어도 오르지 않고, 뒤의 경우 청킹과 k를 아무리 손봐도 오르지 않는다. 두 지표를 따로 재면 진단이 즉시 갈린다.

| 검색이 정답을 가져왔나 | 생성이 근거를 따랐나 | 진단 | 먼저 손댈 곳 |
|---|---|---|---|
| ○ | ○ | 정상 | — (다른 실패 유형을 의심한다) |
| ○ | ✕ | **생성 문제** — 근거 무시 · 컨텍스트 과적재 | 근거 사용을 강제하는 지시, 출처 표기 요구, 넣는 근거 수 줄이기, 온도 낮추기 |
| ✕ | ○ | **검색 문제** — 있는 근거는 잘 썼다 | 청킹 크기·오버랩, 임베딩 모델, top-k, 하이브리드 검색, 리랭킹 |
| ✕ | ✕ | 둘 다 | **검색부터** 고친다. 근거가 틀린 상태에서는 생성 지표를 개선해도 틀린 답을 더 충실히 말할 뿐이다 |

마지막 행이 순서를 정한다 — **검색을 먼저 고친다.** 근거가 잘못된 채로 생성만 다듬으면, 시스템은 잘못된 근거에 더 충실해질 뿐이다.

**구체 사례.** 다섯 지표의 성격은 이렇다.

| 층 | 지표 | 무엇을 재나 | 어떻게 재나 | 어느 실패를 잡나 |
|---|---|---|---|---|
| 검색 | recall@k(재현율) | 정답 청크가 상위 k개 안에 **들어오기라도 했는가** | 질의마다 정답 청크를 미리 표시해 두고, top-k 안에 든 비율을 평균한다 | 검색 실패 · 색인 누락 · 문맥 절단 |
| 검색 | MRR(Mean Reciprocal Rank, 평균 역순위) | 첫 정답이 **몇 등**에 있는가 | 질의마다 첫 정답 순위의 역수(1/순위)를 구해 평균한다. 정답이 없으면 0 | 리랭킹이 필요한지 여부 |
| 검색 | nDCG(normalized Discounted Cumulative Gain) | 관련도가 **여러 등급**일 때 상위 순위가 얼마나 잘 채워졌는가 | 순위가 낮을수록 로그로 할인해 관련도를 누적하고, 이상적 순서의 값으로 나눠 0~1로 만든다 | 잡음 유입 · 순위 품질 전반 |
| 생성 | faithfulness(충실성) | 답변의 각 문장이 **제공된 근거로 뒷받침되는가** | 답변을 문장 단위로 쪼개, 각 문장이 근거 청크에서 도출되는지 판정 모델이나 사람이 채점한다 | 근거 무시 · 인용 조작 · 상충 근거 |
| 생성 | answer relevance(답변 관련성) | 답변이 **질문에 실제로 답하는가** | 답변만 보고 원 질문을 역으로 생성해 원 질문과의 유사도를 재거나, 판정 모델이 직접 채점한다 | 동문서답 · 근거를 그대로 나열만 하는 답 |

앞의 셋은 **정답 청크를 표시한 평가셋만 있으면 코드로 결정적으로 계산된다.** 사람 판단도 모델 호출도 필요 없다는 뜻이고, 그래서 검색 지표를 먼저 세우는 편이 언제나 싸다.

**검색 지표를 직접 계산해 보기.** 질의 세 개짜리 작은 평가셋으로 recall@5와 MRR을 손으로 구하면 두 지표가 무엇을 다르게 보는지 분명해진다.

```
  질의              정답 청크 순위    top-5 포함(1/0)     역순위(1/순위)
  ----------------------------------------------------------------------
  q1 환불 기한      1위               1  (들어옴)         1 / 1  = 1.000
  q2 교환 기한      4위               1  (들어옴)         1 / 4  = 0.250
  q3 배송비 부담    12위              0  (놓침)           1 / 12 = 0.083

  recall@5 = (1 + 1 + 0) / 3             = 0.667
  MRR      = (1.000 + 0.250 + 0.083) / 3 = 0.444
```

두 숫자가 말하는 바가 다르다. **recall@5 = 0.667** 은 「셋 중 둘은 후보 안에 들어와 있다」는 뜻이고, 못 들어온 q3은 리랭킹으로 구제할 수 없으니 **검색 자체**를 고쳐야 한다. **MRR = 0.444** 는 「들어오긴 했어도 위쪽에 있지는 않다」는 뜻이고, q2처럼 4위에 있는 정답은 **리랭킹으로 끌어올릴 수 있다.** recall이 낮으면 검색을, recall은 높은데 MRR이 낮으면 리랭킹을 손보라 — 두 지표를 함께 봐야 나오는 결론이다.

**nDCG는 언제 필요한가.** 위의 두 지표는 「정답이냐 아니냐」의 이분법을 가정한다. 그런데 실제 문서는 **완전히 관련 있음(2) / 부분적으로 관련 있음(1) / 무관(0)** 처럼 등급이 갈리는 경우가 많다. nDCG는 이 등급을 순위에 따라 할인해 더한다.

```
  검색 결과의 관련도 등급이 순서대로 [2, 0, 1] 이라면
    DCG  = 2/log₂(1+1) + 0/log₂(2+1) + 1/log₂(3+1) = 2/1 + 0 + 1/2 = 2.500
  이상적인 순서는 [2, 1, 0] 이므로
    IDCG = 2/log₂2 + 1/log₂3 + 0/log₂4 = 2 + 0.631 + 0 = 2.631
    nDCG = 2.500 / 2.631 = 0.950

  → 2등에 무관 문서가 끼어든 대가로 1.0에서 0.95로 깎였다.
    같은 문서들을 가져왔어도 '순서'가 나쁘면 점수가 떨어진다는 것이 이 지표의 핵심이다.
```

**생성 지표는 어떻게 자동화하나.** faithfulness와 answer relevance는 정답 문자열이 하나로 정해지지 않으므로 단순 비교가 통하지 않는다. 실무에서는 **판정 모델(LLM-as-judge)** 에게 「이 문장이 이 근거에서 도출되는가」를 예/아니오로 묻고 비율을 내는 방식을 쓴다. 다만 판정 모델에는 알려진 편향이 있다 — 앞에 놓인 답을 선호하는 위치 편향, 장황한 답을 선호하는 경향, 자기 계열 모델을 선호하는 경향. 그래서 판정 결과는 **절대 점수보다 같은 평가셋에서의 변화량**으로 읽고, 일정 비율은 사람이 표본 검수해 판정 모델 자체를 검증하는 것이 안전하다.

측정 순서를 하나만 기억한다면 이것이다 — **정답 청크를 표시한 평가셋을 먼저 만들고, 검색 지표부터 세운다.** 이 평가셋은 만드는 데 가장 품이 들지만, 없으면 위의 2×2 표에서 왼쪽 열을 채울 수 없어 진단 자체가 불가능해진다.

**인용.**
- Järvelin, K., Kekäläinen, J., *Cumulated Gain-Based Evaluation of IR Techniques*, ACM Transactions on Information Systems 20(4), 2002 — 등급형 관련도와 순위 할인을 결합한 (n)DCG를 제안한 논문. 오늘날 랭킹 평가의 표준 지표다.
- Es, S., James, J., Espinosa-Anke, L., Schockaert, S., *RAGAS: Automated Evaluation of Retrieval Augmented Generation*, 2023(arXiv:2309.15217) — 정답 레이블 없이 faithfulness·answer relevance 등을 자동 산출하는 평가 틀. 게재처는 확인하지 않았으므로 저자·제목·연도만 밝힌다.
- Zheng, L. et al., *Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena*, NeurIPS 2023(arXiv:2306.05685) — 강력한 LLM을 채점자로 쓰는 방법의 신뢰도와 한계(위치 편향, 장황함 선호, 자기 선호 편향)를 검증한 대표 논문.

**대응 슬라이드: s12**

## 11. 인용 문헌 · 슬라이드 매핑

**정의.** 이 문서에서 인용한 문헌 전체와, 각 절이 강의의 어느 슬라이드에 대응하는지를 모아 둔 절이다.

**원리(무엇을 인용으로 인정했나).** PART 1과 같은 기준이다. 서지 정보는 저자·제목·게재처·연도 수준으로 적었고, **게재처나 연도에 확신이 없는 경우에는 지어내지 않고 저자·제목·연도(및 arXiv 번호)만** 밝혔다. 청킹처럼 아직 정설이 없는 주제는 논문 대신 「정설이 없다」는 사실을 그대로 적었다.

**대응 슬라이드: s08–s13**

---

강의는 s13에서 두 축을 한 장으로 되돌린다 — **「이해하고 지시한다」** 와 **「연결한다」.** 이 문서가 다룬 것은 뒤 축이지만, 읽고 나면 두 축이 사실 하나의 문제를 양쪽에서 밀고 있었다는 것이 보인다. 근거를 찾아 창에 넣는 일(RAG)과 그 근거를 쓰라고 못 박는 일(프롬프팅)은 분리되지 않는다 — 7절의 템플릿과 8절의 검증이 PART 1의 안티패턴·구조화 출력과 같은 문법으로 쓰여 있는 것이 그 증거다. **모델을 이해해 지시하고, 모델이 모르는 것은 찾아 붙인다.** 앞 축의 자세한 논의는 `part1-리터러시와-프롬프트.md`에 있다.
